OceanBase Lakehouse: native Helm deployment
==========================================
Use Docker Compose for a quick database/SQL experience on one machine. Use this
Chart when you already have Kubernetes. Dashboard is enabled by default and is
installed in the SAME Helm release as the lakehouse. No install.sh is shipped in
this Helm Chart, and no Helm process runs inside a Kubernetes Job.

Quick install: database and Dashboard
-------------------------------------
On an empty Kubernetes cluster, the published Chart registers the CRDs and
installs cert-manager and the Operator before it starts the lakehouse.
Run with cluster-level install permissions. All workers need access to the
locked images. Install from the Helm repository or the exact Chart archive:

  helm upgrade --install ob-demo ./oceanbase-lakehouse-*.tgz --namespace ob-demo --create-namespace --wait --wait-for-jobs --timeout 35m

No values file or separate Dashboard installation is needed. The packaged Chart
already pins this delivery's images and enables Dashboard, its monitoring,
bundled MinIO, three LogService processes and one Observer. Suggested worker:
>=8 CPU, 32Gi memory and 350Gi free data disk, with enough allocatable capacity
after other workloads. Successful completion with hooks enabled includes the
database and Dashboard readiness checks. Helm prints access and login commands.

If your StorageClass has another name, append --set storageClass=<actual-name> --set minio.storageClass=<actual-name>.
To reuse a separately managed Dashboard, append --set dashboard.enabled=false.
The progress viewer automatically prefers KUBECONFIG, the current user's
~/.kube/config, then a readable K3s kubeconfig; --kubeconfig always takes precedence.
If the K3s admin kubeconfig is unreadable, it prints an administrator command to create
a private copy and never interrupts the Helm installation.

To reuse a compatible installed Operator, append --skip-crds --set skip-operator=true.
Its served CRDs and admission webhooks must be ready.
These are first-install defaults; keep existing sizing/custom values on upgrades.

Matching release images
-----------------------
Compose and Helm lock their runtime references independently in each channel's
release manifest and image-lock.json. Compose may use wrapper images while Helm
uses the corresponding base images, so references and config image IDs can differ
between channels. The manifest records the upstream component versions and source
relationships. Use the exact images selected for the chosen channel; never copy
or retag an image to impersonate another channel's locked build. Helm also includes
Operator, Dashboard and supporting images; Compose adds its bootstrap runtime.
Config IDs are not registry manifest digests. Check the delivery's
release-defaults.yaml or image-values.yaml for its recorded overrides.

The lightweight configuration artifacts do not include image layers. Use the
matching channel-specific image archive or a registry containing those exact
builds. On a Docker-based
worker, import the matching archive with docker load; on containerd/K3s use that
runtime's import command. Import on every target worker. A local Docker cache is
not automatically available to a separate containerd runtime. Do not substitute
an older Helm image archive or retag different binaries as the current version.
Registry publication/public pull access is not implied by these internal tags.
For optional acceleration while keeping image names unchanged, see
registry-mirrors/README.md in the extracted release bundle. Configure the actual
worker runtime: Docker daemon mirrors do not configure Kubernetes containerd/K3s.

Prerequisites
-------------
- For a fresh cluster, the bundled cert-manager 1.21 supports Kubernetes 1.33
  through 1.36. The Chart's application API floor is Kubernetes 1.27 when
  reusing a compatible Operator and cert-manager. See release acceptance for
  the tested environment.
- Helm 3 and kubectl. The person preparing cluster infrastructure needs
  administrator access. Dashboard creates cluster-scoped permissions when enabled.
- A working StorageClass. Set storageClass and minio.storageClass to its actual name.
- Enough allocatable CPU/memory and disk for the selected profile.
- Workers can pull all configured images (or have the exact images preloaded).
- An existing Operator must serve the lakehouse CRDs and support native storage
  initialization and service resolution. The readiness hook uses the matched
  /lakehouse-readiness image shipped with the Chart.

Check the current context before deployment:
  kubectl config current-context
  kubectl get nodes
  kubectl get storageclass

Single-node experience
----------------------
The quick-install command already selects this sizing. values-single-node.yaml
is an optional explicit copy for customization; image-values.yaml is supplied
for inspection/overrides, and is already incorporated into the packaged Chart.
Suggested worker: >=8 CPU, 32Gi memory, >=350Gi free data disk. The defaults have
one Observer (2 CPU/10Gi), three LogService processes (1 CPU/4Gi EACH), MinIO,
Dashboard, Prometheus and Alertmanager. It uses fixed sizing, not all machine
resources. CPU requests from other Kubernetes workloads count against capacity.

On a multi-node K8s cluster, add a hostname selector in the single-node values
if you want all database Pods on a particular worker, and append
-f values-single-node.yaml to the command. Without a selector Kubernetes may
spread Pods across available workers. A single-node experience has no node-level
high availability.

Three-node experience
---------------------
Copy values-three-nodes.yaml and replace worker-1/2/3 with the actual
kubernetes.io/hostname label values (not assumed public IPs):

  kubectl get nodes -L kubernetes.io/hostname
  helm upgrade --install ob-demo ./oceanbase-lakehouse-*.tgz \
    --namespace ob-demo --create-namespace \
    -f values-three-nodes.yaml \
    --wait --wait-for-jobs --timeout 35m

All workers must be members of one Kubernetes cluster. Kubernetes schedules one
Observer and one LogService per worker. Storage, Dashboard and initialization
run on worker-1 in this example. Budget at least 3 CPU/14Gi per worker for the
database processes, plus the storage/Dashboard/system workloads on worker-1.
Provision adequate capacity beyond these requests. This topology still uses
one bundled MinIO instance; it is an experience setup, not highly available
object storage. For distributed bundled storage on a fresh release, append
-f values-minio-ha.yaml after -f values-three-nodes.yaml. See SHARED-INFRA.md
for disk and placement requirements and for per-volume StorageClass overrides.
For external storage, set objectStorage.endpoint and minio.enabled=false.

No SSH/SCP between workers is performed by Helm. Every worker must be able to
pull the configured images or have the exact images preloaded by an admin.

Common configuration
--------------------
Put custom settings in a values file and keep it for upgrades/reinstalls:

  storageClass: local-path
  observer:
    resource: {cpu: "2", memory: 16Gi}
    dataSize: 100Gi
    logSize: 20Gi
  logService:
    resource: {cpu: "1", memory: 4Gi}
    storeSize: 20Gi
    logSize: 10Gi
  minio:
    size: 100Gi

CPU/memory and disk values are PER PROCESS, not the sum across all replicas.
Observer memory and volume sizing must meet Operator's checks. Larger memory
can require larger data volumes. This guide describes first-install sizing;
changing storage identity or resizing existing state needs a separate planned
procedure. Use --set-string observer.resource.cpu=2 for a simple override; the
old installer flags such as --oc/--nodes are not Helm flags.

For external storage use objectStorage.endpoint=<external-url> and minio.enabled=false, endpoint, region,
logBucket/dataBucket and existingSecret or per-side logExistingSecret and
dataExistingSecret (keys: access_id/access_key). Buckets are checked read-only
by default; createBuckets=true explicitly allows bucket creation. External
credentials/storage are never adopted. LS 1.3 requires virtual-host bucket DNS
for ordinary DNS endpoints. Same-cluster HTTP Service endpoints can be resolved
to ClusterIP; HTTPS names are never replaced by IPs. Bundled MinIO uses the
native Operator resolver without a Helm install/upgrade round trip.

Progress, failure and retry
---------------------------
The Chart declares MinIO, initialization Job, LS, OB and Dashboard together.
Operator waits for successful storage initialization before creating LS zones;
OB waits for LS. A read-only post-install/post-upgrade hook verifies all database
Pods and Dashboard before Helm reports success. Helm --wait alone does not
understand custom-resource readiness; do not use --no-hooks for acceptance.

  kubectl -n ob-demo get pods,jobs,oblogserviceclusters,obclusters
  kubectl -n ob-demo logs -f job/ob-demo-readiness
  kubectl -n ob-demo get jobs -l app.kubernetes.io/component=storage-init
  kubectl -n ob-demo logs job/<storage-init-job-name>
  kubectl -n ob-demo describe pod <pending-or-failed-pod>

The success hook Job is removed automatically. A failed hook is retained for
inspection. Storage initialization Job retries transient failures within its
deadline and is retained until the next Helm revision so Operator can verify
it. After fixing image access, capacity, storage or credentials, rerun the same
helm upgrade --install command. It creates a new initialization Job and hook,
keeps existing data/credentials, and resumes reconciliation. Do not delete a
namespace or rerun with another release name as a retry mechanism. Avoid
--atomic/automatic rollback when first diagnosing a stateful failed install:
retained resources deliberately outlive Helm's cleanup.

Upgrade Operator before starting the lakehouse installation. Do not roll it out
while database bootstrap is in progress: the current Operator task executor
keeps active task handles in memory. If a restart leaves a CR in failed status,
inspect its events and use the Operator's recovery procedure before retrying
Helm. A Helm upgrade does not reset failed database CR status. The retry above
recreates storage initialization; it is not a general database recovery command.

Dashboard and SQL access
------------------------
Kubernetes allocates Dashboard and SQL NodePorts when the default values are 0.
Find the real allocated ports with kubectl -n ob-demo get svc. Use a reachable
node address with those ports. Dashboard's default account is admin.
Use the password retrieval commands printed by Helm. The two accounts are
independent. Direct ALTER USER changes do not update the Kubernetes Secret.

No port-forward process is needed for default access. The client must reach the
node and these TCP ports. Set --set access.host=YOUR-IP-OR-DNS for NAT or multiple
NICs, or when Helm cannot list Nodes. This changes printed addresses only; it
does not configure NAT/firewall rules or assign an address to the node.
On upgrade, Helm reads the existing Service NodePorts and prints direct URLs
when a node address is available. On first install the Services do not exist yet:
access.host supplies the address but cannot supply a port that Kubernetes has
not allocated. Run the post-install commands in NOTES to obtain the actual URL.
Those commands retain access.host when supplied and bracket IPv6 Dashboard hosts.
helm get notes returns the saved installation notes; it does not rerun discovery.
Offline helm template cannot discover node addresses and prints discovery steps.

Override ports with --set dashboard.service.nodePort=31184 and
--set sqlService.nodePort=30882. Use free ports within your cluster's NodePort
range (normally 30000-32767), especially for multiple releases on one cluster.
Existing releases with custom values must explicitly select NodePort to enable it.
To keep both services internal, use --set dashboard.service.type=ClusterIP
--set sqlService.type=ClusterIP. Helm then prints local port-forward guidance.
Dashboard also supports --set dashboard.service.type=LoadBalancer when the
cluster has a load balancer provider.

Retention and uninstall
-----------------------
helm uninstall removes release-managed integration resources and the Dashboard
Deployment. Database CRs, generated credentials, bundled MinIO
StatefulSet/Service/PVC and Dashboard data remain. Reinstall with the SAME
release, namespace and values to reconnect. Helm does not manage Hook resources
on uninstall. After stopping old Helm operations, use the administrator's
prepare.sh --revoke-legacy-binding NAMESPACE RELEASE to remove an abandoned
legacy preparation binding. It checks the exact Hook, role, subject and that
the old Jobs and Pods are inactive before deleting the binding.
Explicitly deleting the namespace or database CRs is destructive and bypasses
this retention; do so only when intentionally removing that experience's data.

Helm history can contain supplied/generated credential values. Protect release
metadata and kubeconfig access. Do not publish rendered manifests containing
Secrets or pass passwords in shell command lines. Use existingSecret references
or --set-file dashboard.adminPassword=/secure/password-file.

Dashboard authentication history migration
-------------------------------------------
From 0.5.7, Dashboard's accounts, bootstrap Secret and authorization policy keep
their existing names and stay outside the ordinary Helm revision manifests.
Fresh installs seed the objects once. An upgrade with an existing Dashboard
keeps the live objects and checks that they are complete.

If Dashboard has been enabled in a release from 0.5.6 or older, pause release
changes before upgrading and make private
backups of the current authentication resources, Helm history and values.
For Helm's default Secret storage driver:

  umask 077
  backup=$(mktemp -d ./lakehouse-auth-backup.XXXXXXXX)
  kubectl -n ob-demo get secret -l owner=helm,name=ob-demo -o json > "$backup/helm-history.json"
  kubectl -n ob-demo get secret ob-demo-user-credentials ob-demo-dashboard-bootstrap -o json > "$backup/dashboard-secrets.json"
  kubectl -n ob-demo get configmap ob-demo-rbac-policy -o json > "$backup/dashboard-policy.json"
  helm get values ob-demo -n ob-demo --all -o yaml > "$backup/values.yaml"

Use the corresponding backup mechanism for other Helm storage drivers. Check
that each backup succeeded and keep it in protected storage. Use the migrated
effective values for the first upgrade. Verify the new revision is deployed,
the current password works and removed users remain revoked. For the explicit
rollback boundary, run a second upgrade with the same new Chart and values:

  helm upgrade ob-demo ./oceanbase-lakehouse-*.tgz -n ob-demo \
    -f migrated-values.yaml --wait --wait-for-jobs --timeout 35m --history-max 1
  helm history ob-demo -n ob-demo

The second upgrade prunes the older rollback history, retaining the first
deployed new revision and the new upgrade revision. Confirm that every listed
revision uses the new Chart before allowing rollbacks. This is an administrator's
explicit choice and removes old revisions from Helm's live history. Restore
data and credentials from private backups or recover by a forward upgrade.
Importing archived pre-migration Helm records into this release would make
unsafe rollback targets available again.

Storage identities and private registries
---------------------------------------
minio.runAsUser/runAsGroup/fsGroup and initialization.runAsUser/runAsGroup/fsGroup
are independent non-root identities (default 10001). The dedicated default
avoids common host login IDs such as 1000, whose named ACL can override the PVC
mode bits. Use IDs assigned by your storage administrator and compatible with
the volume ACL. For example, approved values may be:
  minio: {runAsUser: 10001, runAsGroup: 10001, fsGroup: 10001}
  initialization: {runAsUser: 10001, runAsGroup: 10001, fsGroup: 10001}
The chart does not chown host paths, rewrite ACLs, or run a privileged repair
container. fsGroup behavior depends on the volume driver. Existing PVCs must
already allow the selected identity; changing IDs does not migrate stored data.
The Job's private /work and /tmp must also be writable. MinIO uses OnDelete
updates, so plan a Pod restart for an intentional image/identity change.

Set imagePullSecrets to names of existing Secrets in the release namespace.
The parent references are used by initialization, readiness, Dashboard and
Operator-managed workload ServiceAccounts. Set minio.imagePullSecrets separately.
MinIO and Dashboard each have their own nodeSelector and tolerations; parent
scheduling.* does not automatically place either subchart.

Dashboard privileges and diagnostic images
------------------------------------------
Dashboard manages Kubernetes resources with cluster-wide administrative
permissions. This experience is intended for trusted cluster administrators.
Its generated users/roles, bootstrap password and PVCs survive upgrades and
uninstall. Missing retained authentication must be restored, not regenerated.
The readiness hook only reads namespaced non-secret resources and does not
inherit Dashboard's administrative ServiceAccount.

Log download additionally requires compatible obdiag/oceanbase-helper images
on eligible workers and the Observer's Python tarfile/gzip transport support.
Use the complete image-values.yaml shipped for this build. Native Helm checks
database/Pod/Dashboard readiness; it does not import images, install local
clients or certify that diagnostic log contents are valid. Verify a real log
download when accepting diagnostic capabilities.

Existing staged releases
------------------------
Upgrade Operator first to the matching native build, keep the original values
and render them for review. Use stage=cluster and native.enabled=true. This
Chart preserves the existing CR bucket URLs and credential identity instead of
rewriting immutable storage fields to new DNS URLs. The original release name,
namespace, cluster IDs, buckets, storage Service and PVCs must stay unchanged.
A fresh install keeps Service DNS in the parent CR; Operator resolves only the
same-namespace HTTP Service at runtime for LS 1.3 compatibility. External HTTPS
verification is never weakened, and external Service address drift remains
blocked by the retained storage identity. Changing placement does not move
local-path data. Do not use --force, namespace deletion or a new release name
to work around immutable field checks on an existing database.

Storage selection: see SHARED-INFRA.md for the independent endpoint and minio.enabled controls.
MinIO subchart storageClass/scheduling/imagePullSecrets must be configured under minio.*.

Legacy MinIO upgrades
--------------------
Export helm get values RELEASE -n NAMESPACE --all -o yaml into a protected file.
Run python3 tools/migrate-minio-values.py previous-values.yaml --output migrated-values.yaml,
then pass -f migrated-values.yaml to helm upgrade. The installer performs this
conversion automatically for an installed legacy release. See SHARED-INFRA.md.
