# OceanBase AI 开源交付计划（4.8.0）：Operator、Dashboard、Compose、OBD 与 obshell

日期：2026-10-12。文档状态：方案初稿，供三方评审和排期；工时为增量估算，日期为条件式预计日期，不代表已批准的版本发布承诺。

## 1. 目标与总体判断

本次目标是把 OceanBase AI 的部署、基础管理和湖库试用入口整理为社区用户可获取、可安装、可操作、可排障的完整交付。已有共享存储和日志服务实现可以复用，主要工作是 **4.8.0 适配、开发分支收敛、跨工具联调、真实场景验证、公开制品与文档**。

建议首期提供三种入口：

| 入口 | 用户及使用方式 | 首期交付 |
| --- | --- | --- |
| OBD | 使用 Linux 主机部署的用户，通过配置文件部署 | OceanBase AI、OBLogService 的组合部署与基础生命周期 |
| ob-operator + Dashboard | 使用 Kubernetes 的用户，通过 CR/Helm 或界面管理 | 共享存储集群、日志服务关联、基础资源管理与监控 |
| Docker Compose | 希望快速试用湖库功能的开发者，在一台 Linux 主机启动 | 单 Observer + 三个 OBLogService 进程/容器 + MinIO 的功能演示环境 |

obshell 提供基础管理接口、任务状态和共享存储信息，接口契约由 OBD、Operator/Dashboard 共同消费。具体调用归属按已有实现保留，避免三方重复实现同一管理逻辑。

**初步工作量：开发及联调 61–88 人日，独立 QA 12–18 人日，共 73–106 人日。** 假设 Operator/Compose、OBD、obshell 各有 1 名专职开发，另有 0.5–1 名 QA、发布支持，并且依赖在首周到位，预计 6–8 周形成可公开发布版本。若 T0 为 2026-10-12，预计窗口为 **2026-11-20 至 2026-12-04**。实际发布日以 4.8.0 核心包、回归结果及正式发布审批为准。

## 3. 支持能力范围

P0 是首期计划交付及验收范围；P1 是单独排期的后续能力。下表描述目标范围，并非宣布当前全部可用。

| 能力 | P0 范围及边界 | P1/待确认 |
| --- | --- | --- |
| 安装部署 | 4.8.0 官方社区包/镜像组合；OBD 主机部署、Operator Kubernetes 部署、Compose 单机试用 | ARM64、更多 OS/Kubernetes 版本须有对应制品和测试证据后进入支持矩阵 |
| 湖库/共享存储 | 新建共享存储集群，配置对象存储，关联日志服务，完成 bootstrap 和 SQL 读写 | 传统存储集群原地转换为共享存储不纳入首期承诺 |
| 日志服务 | 新建、健康检查、停止/启动或重启、节点与集群状态、依赖顺序、失败重试与数据保护 | 跨地域容灾、自动副本重构、在线升级/复杂拓扑调整单独验收 |
| 对象存储 | 首先验证 MinIO/S3 兼容路径，统一 endpoint、region、寻址方式及 bucket/prefix 规则 | OSS、COS 和其他厂商作为候选；代码有类型支持不等于已经完成认证 |
| 基础管理 | 租户创建与 SQL 连接、配置校验、状态展示、正常重启及数据保留、删除语义 | 在线扩缩容与备份恢复作为独立能力门禁；未经验证的入口应关闭或明确限制 |
| Dashboard/监控 | 集群/租户/日志服务概览、共享存储容量、基本查询、失败原因和告警/日志入口 | 深度诊断、自动调优、高级多集群管理按需求另排 |
| AI/湖库体验 | 以正式 4.8.0 社区内核实际开放能力为准，提供基础 SQL 与湖库示例；向量/检索等示例在内核确认后加入 | 不在工具侧承诺模型托管、训练、GPU 调度或完整 RAG 平台；相关服务/密钥需另列依赖 |
| 安全 | 管理接口认证、角色/namespace 隔离、凭据存储与脱敏、下载及参数输入校验、制品扫描 | 企业权限集成和额外认证体系由需求单独定义 |
| 升级 | 首期必须阻止未经验证的版本组合和不支持的升级；文档给出可验证的安装/重建路径 | 在线滚动升级、跨架构迁移和自动回滚不在未验证时宣称支持 |

Compose 的三个日志容器运行在同一主机上，仅用于功能验证，不能据此宣称高可用。现有 README 的建议资源为 16 核、32 GiB 可用内存、60 GiB 空闲磁盘，首期需要在正式镜像上测出实际最低和推荐规格，并修正文档。

## 7. 主要风险与处理方式

| 风险 | 影响 | 处理方式/决策门禁 |
| --- | --- | --- |
| 4.8.0 与当前 4.6.x 参数/API/视图不同 | 开发返工，已有测试失效 | M1 冻结组合，按正式包重新验证；跨版本调用设置能力守卫 |
| 三方参数及状态语义不一致 | 一个工具部署成功、另一个无法管理 | X1 统一契约，跨工具同一集群联测，错误码和资源口径可追踪 |
| 部署重复执行或失败恢复覆盖已有数据 | 数据丢失、无法恢复 | 严禁以清盘替代重试；记录归属，使用独立 bucket/prefix；保留/销毁入口分开验收 |
| 三节点同机被误认作高可用 | 用户错误选型 | Compose 明确单机试用，生产能力用独立故障域和真实故障测试证明 |
| 存储寻址方式/权限/延迟差异 | bootstrap 或运行时 I/O 失败 | MinIO/S3 先过；逐厂商认证；覆盖网络中断、权限拒绝和超时 |
| 内部包或镜像无法公开获取 | “代码开源”但用户无法安装 | X2 固定公开获取入口和校验值，洁净环境无内部网络复验 |
| Compose 使用 latest、root 空密码或本地编译 | 不可复现、试用暴露风险、用户门槛高 | 固定镜像 digest、初始化密码、合理监听地址、发布 bootstrap 镜像 |
| Dashboard/obshell 暴露凭据或权限边界不完整 | 安全阻断 | 认证/鉴权、脱敏、SQL/命令输入边界及下载权限纳入 Q1 |
| 测试修复未进入正式分支 | 发布后旧缺陷重现 | O1/D4/S4 核对 release SHA、合入清单和制品来源 |
| 把扩缩容/升级/备份恢复默认算作已有能力 | 工时漏算，发布承诺过大 | P1 单独排期；未认证接口关闭或明确限制，不复用传统模式结果 |
| 开发和 QA 资源被其他缺陷占用 | 时间窗口顺延 | M1 锁定资源；按剩余人日每周更新，必要时缩减首期范围 |

## 8. 发布验收清单

1. 能力矩阵明确，所有制品和工具版本可对应到 release SHA、tag/digest、校验值；社区下载和离线安装可用。
2. 三个入口均能在洁净环境按公开文档启动；日志服务先就绪，对象存储配置正确，SQL 读写成功。
3. 正常重启、重复执行、失败重试和 down/up 不丢已写入数据；销毁只处理本次资源，数据删除语义明确。
4. 真实环境验证进程/Pod 故障、对象存储不可达、错误凭据、资源不足和端口冲突；状态、错误和恢复步骤一致。
5. Dashboard/obshell 的共享存储容量与底层视图一致；权限、凭据和输入边界测试通过。
6. 普通存储部署、租户基础管理等既有路径回归通过；未支持功能有明确限制。
7. 单项缺陷修复按各项目流程测试；本项目 DIMA 修复由 3 个独立 subagent 实跑通过后回填 Fixed。此流程不能替代整版 QA 和稳定性验收。
8. 正式候选制品通过 48–72 小时稳定性观察和社区安装复验；公开文档、中英文快速入门、已知限制、故障手册和许可证/SBOM 齐备。
